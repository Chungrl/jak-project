## 1. What it is

This is a **C++23/CMake Skate 3 recompilation application**, not a Rust crate or a gameplay library. CMake builds a `skate3` executable, links the ReXGlue runtime and a separate `skate_owned_world` static library, then adds generated retail executable sources to the game target ([CMakeLists.txt:351–353](https://github.com/tvllerr/SK8-Engine/blob/main/CMakeLists.txt#L351-L353), [CMakeLists.txt:545–567](https://github.com/tvllerr/SK8-Engine/blob/main/CMakeLists.txt#L545-L567)). That owned-world library contains map, collision, grind-spline, rendering, and Box3D object code; its physics header says the retail skater and board controller remains in charge ([owned/world/CMakeLists.txt:42–67](https://github.com/tvllerr/SK8-Engine/blob/main/owned/world/CMakeLists.txt#L42-L67), [box3d_physics.h:69–76](https://github.com/tvllerr/SK8-Engine/blob/main/owned/world/include/skate/world/box3d_physics.h#L69-L76)).

**Gameplay lines cannot be counted reliably from the checked-in source:** the original gameplay is generated from the user’s retail executables; that generated tree was unavailable to this audit. The checked-in trick pipeline alone is about 6,000 lines of hooks and observation, not a standalone Skate simulation. Tests exist for owned-world and optional protocol/DLSS code ([owned/world/CMakeLists.txt:75–101](https://github.com/tvllerr/SK8-Engine/blob/main/owned/world/CMakeLists.txt#L75-L101), [CMakeLists.txt:669–685](https://github.com/tvllerr/SK8-Engine/blob/main/CMakeLists.txt#L669-L685)); I did not run them or verify playability. The inspectable public branch’s latest commit is **28 August 2026**, a release-manifest update ([commit](https://github.com/tvllerr/SK8-Engine/commit/311cd40e8a8f2c824586e4485f79d8aee8dcde8b)).

| Board integration; manuals; pushing/carving; bails | **(a).** The owned physics world mirrors the retail player as a kinematic proxy rather than replacing its controller; the bridge runs after `SkateboardController::FillPhysOut` ([box3d_physics.h:69–76](https://github.com/tvllerr/SK8-Engine/blob/main/owned/world/include/skate/world/box3d_physics.h#L69-L76), [skate3_mechanics_sandbox.h:83–89](https://github.com/tvllerr/SK8-Engine/blob/main/src/skate3_mechanics_sandbox.h#L83-L89)). Separate portable implementations or parity fixtures for these behaviors: **not found**. |
| Grinding | **(a) retail grind behavior**, fed by project-owned authored rail data. The adapter converts rails to Pegasus `tSplineData` and registers them with retail `GrindData` ([skate3_native_grind.h:18–24](https://github.com/tvllerr/SK8-Engine/blob/main/src/skate3_native_grind.h#L18-L24)). |
| Animation selection | **(a) retail animation tree**, with project hooks and an optional new custom trick. ## 3. Proprietary content

The checked-in code includes **function-address manifests and adapters**, plus original world/tool code; generated retail function bodies are added only when `generated/sources.cmake` exists ([CMakeLists.txt:545–550](https://github.com/tvllerr/SK8-Engine/blob/main/CMakeLists.txt#L545-L550)). Code generation invokes ReXGlue on `default.xex` and `EAWebkit.xex` ([cmake/CodegenTargets.cmake:1–19](https://github.com/tvllerr/SK8-Engine/blob/main/cmake/CodegenTargets.cmake#L1-L19)). CMake expects a user-supplied extracted game root and can consume a user-supplied title-update package or XEXP files ([CMakeLists.txt:85–92](https://github.com/tvllerr/SK8-Engine/blob/main/CMakeLists.txt#L85-L92), [CMakeLists.txt:224–233](https://github.com/tvllerr/SK8-Engine/blob/main/CMakeLists.txt#L224-L233)). In-repository ISO/XEX, extracted retail assets, animation clips, and generated retail code: **not found in the inspected public source**. Runtime staging includes title-update XEXP files ([CMakeLists.txt:639–657](https://github.com/tvllerr/SK8-Engine/blob/main/CMakeLists.txt#L639-L657)).

## 5. Architecture for embedding

There is **no headless gameplay `step(input, world) -> state` API, world-query trait, C ABI, or per-frame host IPC bridge found**. `OwnedPhysicsWorld::Step(double)` advances *map objects* at 60 Hz with four Box3D substeps ([box3d_physics.h:11–15, 69–76](https://github.com/tvllerr/SK8-Engine/blob/main/owned/world/include/skate/world/box3d_physics.h#L11-L76)). Its map data uses right-handed, Y-up metres, triangles, materials, and separate grind rails; `WorldMap` offers ray and sphere queries ([world_map.h:367–380](https://github.com/tvllerr/SK8-Engine/blob/main/owned/world/include/skate/world/world_map.h#L367-L380), [world_map.h:783–803](https://github.com/tvllerr/SK8-Engine/blob/main/owned/world/include/skate/world/world_map.h#L783-L803)). The Windows named pipe is an **input/telemetry lab** with `SET`, `QUEUE`, and snapshot commands, not a simulation worker protocol ([skate3_input_lab.cpp:983–1094](https://github.com/tvllerr/SK8-Engine/blob/main/src/skate3_input_lab.cpp#L983-L1094)). A general pose export, standard skeleton bone count, and Jak-skeleton retargeting interface: **not found**.

## 6. Reusability verdict

**Liftable:** authored-map geometry, surface data, query code, and perhaps the outer-circle *custom* recognizer after removing guest-input coupling. **Not liftable as a gameplay library:** retail Flickit, board motion, grind response, manuals, bails, and animation depend on the generated game/runtime and retail data. A worker process would still have to run that whole game stack and exchange collision, state, and pose through a protocol that does not exist. For Jak 3, the practical route is a new gameplay implementation using these hooks as research evidence; rough effort for a credible **stick → trick → board-motion** prototype is **months, not a small integration**, with animation and collision parity the main risks.
