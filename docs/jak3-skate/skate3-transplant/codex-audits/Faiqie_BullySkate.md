## 1. What it is

A Rust 2024/Cargo skating simulation and Windows worker, with a C/C++ x86 Bully adapter, C# launcher, Python extractors, and a separate Rust audio worker. Cargo defines `SkatePhysicsWorker` and a `staticlib`; the gameplay-facing crate, `bully-skate-runtime`, is an `rlib` depending on vendored `skate-core`, `skate-data`, `skate-net`, and `skate-dynamics`. [Cargo.toml](https://github.com/Faiqie/BullySkate/blob/main/Cargo.toml#L1-L28), [skate-runtime/Cargo.toml](https://github.com/Faiqie/BullySkate/blob/main/skate-runtime/Cargo.toml#L1-L14)

A source-tree size count suggests **roughly 100,000–140,000 lines** across gameplay, physics, graph, animation, and data code (`skate-runtime/src` plus vendored rewrite: about 6.2 MB), versus roughly 10,000–20,000 lines of native adapter, launcher, extractor, audio worker, and bridge code. Those are byte-based estimates, not measured LOC or a clean gameplay/engine split. The source has unit tests, integration tests, and probes; v0.1.2 was released, so it is more than a stub. Playability and test results were **not checked**. [Source tree](https://github.com/Faiqie/BullySkate/tree/main/skate-runtime/src), [tests](https://github.com/Faiqie/BullySkate/tree/main/tests)

## 3. Proprietary content

The repository ships source, format readers, a TU3-derived gesture mapping table, extraction names/checksums, and an authored Bully action bank. The inspected tree showed **no ISO, XEX, extracted stock animation banks, sound banks, or converted game assets**. At setup, the user supplies `default.xex` beside `miscload.big`, `miscboot.big`, and `db.big`; extraction obtains `.pat` patterns, state graphs, animation banks, and physics/skeleton data, then verifies 18 required files. Runtime loading needs those extracted files. [extract.py:14–17,46–106](https://github.com/Faiqie/BullySkate/blob/main/extractor/extract.py#L14-L106)

## 5. Architecture for embedding

There is a headless Rust simulation path, though not a small engine-agnostic gameplay package. `SkateHost::tick(&mut self, XboxState) -> Result<(), String>` advances input, gestures, graphs, physics, and animation; callers read `output() -> [f32;14]`, `pose()`, board pose, and state. It loads stock assets at construction. The physics step is **fixed 60 Hz**; the worker accumulates host `dt` and calls `tick` as needed. Core coordinates are **Y-up metres**; the Bully bridge swaps/sign-flips axes. A separate handedness declaration was **not found**. [lib.rs:27–57,177–200](https://github.com/Faiqie/BullySkate/blob/main/skate-runtime/src/lib.rs#L27-L57), [settings.rs:65–72](https://github.com/Faiqie/BullySkate/blob/main/skate-runtime/src/physics/settings.rs#L65-L72), [skate_worker.rs:107–123](https://github.com/Faiqie/BullySkate/blob/main/src/skate_worker.rs#L107-L123)

World input is triangle collision with materials/edge data plus grind rails. `ExternalQueries` supplies swept line hits and nearby moving triangles; static world and grind providers currently ingest map data rather than an OpenGOAL callback. The runtime uses Bevy math/resources, Rapier through `skate-dynamics`, and other Rust crates. Its `rlib` has **no gameplay C ABI**; the root `staticlib` exports only a deadzone function. The existing Windows worker uses named shared memory/events to exchange queued buttons/axes, actors, vehicles, and world selection for board state, 36 Bully bone transforms, camera, and audio. Animation clips and source bone names come from extracted banks; Jak needs its own retarget and pose format. [board_world.rs:25–49,104–115](https://github.com/Faiqie/BullySkate/blob/main/vendor/skate-rewrite/crates/skate-core/src/physics/board_world.rs#L25-L115), [skate_worker.rs:15–32](https://github.com/Faiqie/BullySkate/blob/main/src/skate_worker.rs#L15-L32), [src/lib.rs:8–12](https://github.com/Faiqie/BullySkate/blob/main/src/lib.rs#L8-L12)

## 6. Reusability verdict

**Separate worker is the shortest technical route**, after obtaining clear rights: adapt `SkateHost`, `skate-core` gesture/board code, and the existing frame protocol. Replace Bully geometry/rails, material mapping, actors, camera, and 36-bone retarget with OpenGOAL inputs and Jak pose output. A direct library needs a new C ABI and ownership/error boundary. Gesture recognition alone is smaller, but still needs the player’s `.pat` data; **stick → recognized trick → physical board motion** also needs stock graphs, settings, solver, and collision. Rough estimate: **several weeks for a constrained prototype; months for a robust Jak integration**, with source-data rights and character animation the largest risks.
